# GitHub: как работать с проектом без программирования

Этот проект лучше хранить на GitHub так:

- в репозитории лежат исходники: `.py`, `README.md`, `PROJECT_NOTES.md`, `requirements.txt`, `tests/`, `sounds/`;
- готовые `.exe`, папки `build/` и `dist/`, логи и кэши не хранятся в обычной истории Git;
- готовые версии для запуска лучше выкладывать в GitHub Releases отдельными файлами.

## Почему так

Исходники маленькие, их удобно сравнивать и объединять. Готовые `.exe` большие, часто пересобираются и плохо показывают, что именно изменилось.

## Простая схема работы

1. Перед началом новой задачи нажмите в GitHub Desktop `Fetch origin` / `Pull origin`, чтобы забрать свежую версию.
2. Создайте новую ветку под задачу. Пример: `fix-gate-connect`, `add-bitget`, `change-alert-sound`.
3. Попросите нейронку внести изменения в этой ветке.
4. Проверьте, что программа запускается или что нужный тест проходит.
5. Сделайте commit с коротким описанием.
6. Нажмите `Push origin`.
7. Создайте Pull Request на GitHub.
8. Второй человек смотрит изменения и только потом вливает их в `main`.

## Важные правила

- Не работайте вдвоём прямо в `main`.
- Не добавляйте в GitHub папки `build/` и `dist/`.
- Если меняете готовый `.exe`, выкладывайте его как Release, а не обычным commit.
- Если GitHub Desktop показывает conflict, ничего страшного: остановитесь и попросите Codex/нейронку помочь решить конфликт.

## Что делать с config.json

`config.json` сейчас можно хранить как стартовый пример списка монет. Но если у каждого пользователя будет свой личный список, лучше позже сделать отдельный `config.example.json`, а личный `config.json` убрать из Git.
