# Рабочий процесс проекта

Этот файл нужен, чтобы работать с проектом спокойно: с Codex, с коллегой,
с GitHub и без необходимости помнить технические детали.

## Перед началом любой задачи

1. Убедиться, что работа начинается из свежей версии проекта.
   - В GitHub Desktop: `Fetch origin`, потом `Pull origin`.
   - Если работа идёт через Codex, можно попросить: "проверь статус git".
2. Открыть задачу отдельной веткой.
   - Примеры названий: `fix-zero-life-filter`, `add-bitget`, `improve-alert-feed`.
   - Не работать вдвоём прямо в `main`.
3. Перед правками коротко записать цель:
   - что сейчас не так;
   - как должно быть;
   - как проверить глазами или тестом.

## Как ставить задачу Codex

Лучший формат:

```text
Хочу изменить: ...
Сейчас работает так: ...
Нужно, чтобы было так: ...
Как проверить: ...
Скрин/пример: ...
```

Пример:

```text
Хочу исправить фильтры плотности.
Сейчас при Дистанция 0 и Жизнь 0 плотности не попадают в ленту.
Нужно, чтобы Жизнь 0 означала мгновенный алерт, а Дистанция 0 искала у спреда.
Проверка: добавляю BANKUSDT, ставлю оба фильтра 0, плотность у спреда появляется в ленте.
```

## Что Codex должен делать по задаче

1. Прочитать relevant-код и `PROJECT_NOTES.md`.
2. Внести изменения в код.
3. Добавить или обновить тесты под новый сценарий.
4. Запустить важные тесты.
5. Если менялся интерфейс, запустить приложение и проверить окно.
6. Пересобрать exe через `build.bat`, если нужна готовая версия.
7. Коротко объяснить, что изменилось и как проверить.

## Минимальный стандарт готовности

Задача считается готовой, если:

- приложение запускается без Tkinter-ошибок;
- важный сценарий из задачи проверен тестом или руками;
- старые критичные сценарии не сломались;
- если нужен exe, он пересобран;
- в ответе понятно написано, что именно изменилось.

## Работа с коллегой

1. Каждый делает отдельную ветку под одну задачу.
2. Не менять одновременно один и тот же кусок интерфейса без договорённости.
3. После задачи писать короткий итог:
   - что изменено;
   - какие тесты пройдены;
   - где готовый exe, если он нужен.
4. Вливать изменения в `main` только после проверки.
5. Если появился конфликт GitHub, не пытаться решать наугад. Попросить Codex
   или другую нейронку разобрать конфликт.

## Что не хранить в GitHub

Не коммитить:

- `build/`;
- `dist/`;
- `.exe`;
- `debug.log`;
- временные скриншоты `screen-check-*.png`;
- диагностические архивы `debug_packs/`.

Готовые exe лучше выкладывать в GitHub Releases, а не обычным commit.

## Основные файлы для ориентации

- `PROJECT_NOTES.md` - полное состояние проекта и смысл функций.
- `README.md` - как запустить и пользоваться.
- `RELEASE_CHECKLIST.md` - что проверить перед выдачей версии.
- `CHANGELOG.md` - история изменений.
- `BUGS.md` - список известных проблем и шаблон для новых.
- `GITHUB_START_HERE.md` - простое объяснение GitHub-процесса.
- `BUILDING.md` - подробная инструкция для Codex/Claude: сборка exe, Tkinter/Tcl пути,
  тесты, версионные копии и правила, какие файлы не коммитить.
